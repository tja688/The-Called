## 1. 本轮设计结论

这是一套双方在 **3×3 棋盘上轮流打出一张牌**的占格对战。

- 玩家固定先手。
- 双方交替行动，每个行动回合通常只打出 1 张牌。
- 卡牌具有 Power 和效果；当前牌池中的卡都作为场上牌进入棋盘，而不是打完即弃的法术牌。
- 普通情况下，牌可以放进空格；也可以用 Power **严格更高**的牌覆盖敌方牌。
- 打出的牌从手牌移至棋盘，不会回到抽牌堆，也不会再次抽到。
- 手牌最多 5 张。自己的行动回合开始时抽 1 张；达到上限时不抽。
- 当 3×3 的 9 个格子都被场上牌占据时，计算双方场上总 Power，较高者获胜。
- 空间关系只用于触发卡牌效果，不额外提供连线分数。
- 本阶段不增加非必要 UI，只在卡牌正面和现有 HUD 中显示完成操作所必需的信息。

### 1.1 本文暂不处理

- 第二节点怪物及其牌库。
- Moon 的正式牌库和 AI 策略。
- BO3、局间奖励、同化、精神和谐度、污染等 Roguelite 系统。
- 完整卡面美术、动画细化和额外界面设计。
- 新流派、新卡牌或现有卡牌的数值平衡。

## 2. 对 HTS Version 的检查结果

### 2.1 应继承的玩法信息

HTS 原型已经实现并验证了以下底层逻辑，建议作为新版基础：

1. 双方交替，每次打出 1 张手牌。
2. 卡可以进入空格。
3. 只有攻击牌 Power 严格高于目标牌时，才能覆盖敌方牌。
4. 普通卡不能覆盖己方卡；效果明确允许移动、替换或叠放时除外。
5. 一个动作应先验证是否合法，再消耗手牌和改变棋盘。
6. 卡牌效果需要明确目标类型与结算时机。
7. AI 不应只随机出牌，而应枚举合法的“卡牌 × 落点 × 效果目标”组合，再依据策略评分。
8. 场上总 Power 是终局胜负的核心计算值。

### 2.2 不应原样继承的旧规则

| HTS 原型 | 本版规则 |
|---|---|
| 2×4，共 8 格 | 3×3，共 9 格 |
| 随机决定先手 | 玩家固定先手 |
| 开局 3 张，后手额外 1 张 | 暂定双方起手 5 张，不再提供后手补牌 |
| 手牌没有上限 | 手牌上限 5 张 |
| 下一行动者切换后抽 1 张 | 每个行动回合开始抽 1 张，上限 5 |
| 满盘、全占、无行动等多种终局 | 当前明确规则以 9 格被牌铺满后比较总 Power 为主 |
| 平分时玩家直接获胜 | 本版尚未确认平局规则 |
| BO3 与局间构筑 | 当前单局玩法不接入 |

### 2.3 HTS 中需要避免的实现问题

- HTS 引擎在验证落点之前先从手牌移除卡牌；虽然 UI 通常阻止非法点击，但底层仍可能让非法动作吞牌。新版必须采用“先验证、再提交”的原子动作。
- HTS 的 Seal / Ban 会减少可填充格，却仍以“没有空格”作为部分终局条件，容易产生规则歧义。新版终局必须明确只统计被卡牌占据的 9 格。
- HTS 的手牌持续增长，没有上限检查；新版所有抽牌入口都必须经过同一个 `handLimit = 5` 规则。
- HTS 的邻接表只适用于 2×4。新版统一使用当前 Strix 已有的 3×3 空间工具。

## 3. 单局结构

### 3.1 对局区域

每一方拥有：

- 一个固定牌库。
- 一组手牌，最多 5 张。
- 棋盘上由自己控制的牌。
- 一个弃置 / 移出区，仅用于保存被覆盖或效果移除的实例；这些牌不会重新洗回牌库。

双方共享：

- 一个 3×3 棋盘，共 9 格。
- 回合归属和效果结算队列。

### 3.2 开局流程

建议流程：

1. 根据当前关卡配置加载怪物、场景、怪物牌库和怪物策略。
2. 创建空的 3×3 棋盘。
3. 双方牌库分别洗牌。
4. 双方各抽 5 张作为起手牌。
5. 玩家固定先手。
6. 首个玩家回合不再额外抽牌；从双方各自的第二次行动开始，回合开始抽 1 张。

采用第 4–6 条的原因：当前画面已经以 5 张手牌为标准，直接起手 5 张最符合现有交互；如果首回合仍抽牌，会立刻触发上限而形成没有意义的抽牌步骤。

> **待验收 A：** 是否确认“双方起手 5 张，首回合不抽；之后各自行动开始抽 1 张”？如果希望起手 4 张、玩家第一回合抽到 5 张，也可以调整，底层规则不受影响。

### 3.3 行动回合流程

```text
回合开始
  ↓
处理“持续到本回合开始”的到期效果
  ↓
若不是该角色的首次行动：抽 1 张（手牌达到 5 时跳过）
  ↓
选择 1 张手牌
  ↓
显示合法落点
  ↓
如卡牌需要目标，选择合法目标
  ↓
再次验证完整动作
  ↓
卡牌进入落点 / 覆盖目标
  ↓
结算入场、覆盖、移动、生成及临时效果
  ↓
检查 9 格是否全部被牌占据
  ↓
若未结束，切换行动方
```

### 3.4 抽牌与手牌上限

- `handLimit = 5`。
- 抽牌时，如果手牌少于 5 张且牌库非空，则抽牌堆顶 1 张。
- 如果手牌已有 5 张，本次抽牌跳过；牌仍留在牌库中，不弃置、不烧毁。
- 如果牌库为空，本次抽牌跳过。
- 效果生成到手牌的卡同样受 5 张上限约束；超出时默认生成失败。
- 已打出的牌离开手牌并成为场上实例。
- 被覆盖或移除的牌进入移出区，不返回牌库。

> **待验收 B：** 手牌已满时，建议采用“不抽且牌留在牌库”；如果你希望满手时烧掉牌库顶牌，需要另行确认。

## 4. 落牌、覆盖与控制权

### 4.1 空格落牌

- 没有特殊限制时，手牌可以放入任意空格。
- 落牌后，该格由出牌方控制，卡牌 Power 计入出牌方总 Power。
- 落牌产生的效果按第 5 节时序处理。

### 4.2 覆盖敌方牌

- 当手牌当前 Power **严格大于**敌方目标牌的当前 Power 时，可以直接打到该格。
- 原敌方牌被覆盖并移出棋盘。
- 新牌占据该格并归出牌方控制。
- Power 相等时不能覆盖。
- Power 较低时不能覆盖。
- 非法覆盖不会消耗卡牌，也不会结束行动回合。

### 4.3 覆盖己方牌

- 默认禁止用手牌直接覆盖己方牌。
- 明确写有“移动”“交换”“替换”“叠放”或“献祭”的效果可以改变己方牌位置或移除己方牌。
- 移动不是重新打出，不重复触发“出场效果”，除非卡牌文本明确说明。

### 4.4 “吃掉”的统一定义

本文将口语中的“吃掉”统一定义为“覆盖”：

1. 检查打出牌 Power 是否严格更高。
2. 令被覆盖牌离场。
3. 新牌占据原位置。
4. 新牌才开始结算自身出场效果。

如果未来加入“被覆盖时”效果，应插入第 2 步之后、新牌出场效果之前。

## 5. 效果系统与结算时序

### 5.1 卡牌效果的基础格式

开发时每张牌建议拆成以下字段，而不是依赖一段不可执行的自然语言：

```ts
type CardDefinition = {
  id: string
  name: string
  owner: 'player' | 'monster'
  power: number
  category: string
  rulesText: string
  placementRule: PlacementRule
  effects: CardEffect[]
}

type CardEffect = {
  timing: 'on-play' | 'on-enter' | 'on-covered' | 'turn-start' | 'turn-end'
  condition?: EffectCondition
  target?: TargetRule
  actions: EffectAction[]
  duration?: EffectDuration
}
```

这样怪物牌库、玩家牌库和 AI 策略可以继续保持独立配置。

### 5.2 单次出牌结算顺序

统一顺序暂定为：

1. **动作合法性检查**：卡牌在手、轮到该方、落点合法、目标合法、条件满足。
2. **提交动作**：从手牌移除该实例。
3. **覆盖结算**：若落点有敌方牌，先处理其离场。
4. **卡牌入场**：打出的牌占据落点。
5. **本牌出场效果**：依卡牌配置顺序执行。
6. **数值更新**：重新计算当前 Power。
7. **终局检查**。

### 5.3 Power 的组成

首战只需要区分基础 Power 与永久修正：

```text
当前 Power
= 基础 Power
+ 永久修正
```

- 覆盖判定和终局计分都读取当前 Power。
- Power 最低暂定为 0，不允许出现负数。
- 首战卡牌产生的 `+1 / -1` 都属于永久修正，在该牌离场前持续有效。
- 后续怪物若需要临时修正，再扩展持续时间字段；首战不提前引入。

### 5.4 空间定义

- **相邻**：默认指正交相邻，即上、下、左、右；不包含斜角。
- **合法空格**：没有场上牌的格子。
- **边缘格**：3×3 外圈的 8 个格，中心格不属于边缘。

首战牌库不使用移动、交换、封锁或额外棋盘实体；这些定义仅为后续扩展预留。

## 6. 终局与计分

### 6.1 标准终局

每次完整动作结算结束后检查棋盘：

- 当 9 个格子全部由卡牌占据时，单局立即结束。
- 临时禁止直接落牌的空格仍然是空格，不算铺满。
- 被特殊效果延伸到棋盘外的阴影不属于 3×3 格子，不计入铺满数量。

### 6.2 总 Power

```text
玩家总 Power = 所有玩家控制的场上牌当前 Power 之和
怪物总 Power = 所有怪物控制的场上牌当前 Power 之和
```

- 较高者获胜。
- 空间连线不额外计分。
- 卡牌种类、占格数量本身不额外计分。
- 所有仍在场上的永久 Power 修正参与终局计算。

> **待验收 C：** 总 Power 相同时如何处理尚未指定。建议首版记为平局，避免暗藏先后手偏置；也可以指定怪物胜或玩家胜。

### 6.3 极端状态

以下状态不会被“满盘”规则自然解决，需要先确定统一处理：

- 当前行动方有牌但没有任何合法落点或合法覆盖。
- 双方牌库和手牌都为空，但棋盘仍未铺满。
- 双方剩余手牌都无法覆盖对手，也没有可用空格。

建议首版加入“双方连续各一次无合法行动”终止条件，随后比较总 Power。单方无合法行动时跳过，不直接判负。

> **待验收 D：** 是否接受“单方无行动则跳过；双方连续无行动则按总 Power 结算”？

## 7. Game Jam 新手牌池

### 7.1 设计目标

第一场战斗只教学四件事：

1. 把牌放进空格。
2. 更高 Power 可以覆盖更低 Power。
3. 相邻位置可以产生简单的 `+1` 或 `-1`。
4. 棋盘铺满后比较双方总 Power。

因此，本版牌池主动删除以下机制：投影点、本影、Umbra、特殊生成、移动、交换、封锁格、场地状态、临时 Power、印刷值重置、禁止强化和多阶段目标。旧名称可以保留怪物气质，但不再承载额外系统。

首战所有 Power 改变均为**永久改变**：只要牌仍在场上，修改后的数值就一直有效。效果没有合法目标时直接跳过，卡牌仍可正常进入棋盘，避免新手因不理解效果而无法出牌。

### 7.2 SVARBHĀNU 新手牌库

### 7.4 首战效果模板

首战只需要实现以下四种效果模板：

| 模板 ID | 含义 | 使用卡牌 |
|---|---|---|
| `none` | 无额外效果 | 遮光体、黑箱模型、失光残影、基准点、观测记录 |
| `self_power_if_position` | 满足落点或邻接条件时，本牌永久 +1 | 偏轴投影、边界收束、失真读数、边界条件 |
| `adjacent_power_change` | 自动使所有符合阵营条件的相邻牌永久 +1 或 -1 | 不可观测区、校准、误差修正 |
| `self_power_on_cover` | 成功覆盖敌方牌后，本牌永久 +1 | 反证 |

这四种模板全部建立在基础 Power 规则上，不引入新的棋盘实体或额外阶段。

## 8. SVARBHĀNU 的新手策略框架

策略应独立于卡牌定义。卡牌定义描述“牌能做什么”，策略配置描述“怪物倾向怎么选择”。

### 8.1 策略配置建议

```ts
type MonsterStrategy = {
  id: string
  monsterId: string
  priorities: StrategyRule[]
  tieBreak: 'deterministic' | 'seeded-random'
}

type StrategyRule = {
  when: StrategyCondition
  score: number
  reason: string
}
```

AI 每回合的流程：

1. 枚举手中每张牌的全部合法落点。
2. 若牌有效果目标，继续枚举全部合法目标。
3. 模拟动作结算后的棋盘。
4. 按策略规则计算总分。
5. 选择最高分动作；同分时用固定种子随机，保证可复现。

### 8.2 SVARBHĀNU 的建议人格

SVARBHĀNU 是第一个教学怪物。它应该做出看起来合理、但不会持续计算多步组合的选择：

1. 有牌能够覆盖玩家牌时，优先覆盖。
2. 无法覆盖时，优先让当前打出的牌获得 `+1`。
3. `不可观测区` 优先削弱 Power 最高的相邻玩家牌。
4. 其次选择中心格，再选择边缘格。
5. 不为未来回合保留关键牌，不预测玩家手牌。

这会自然演示“高牌吃低牌”“落点影响点数”和“相邻效果”，同时给玩家留下可理解、可利用的失误空间。

### 8.3 初版评分维度

| 行为结果 | 建议权重方向 |
|---|---:|
| 覆盖玩家高 Power 牌 | 高 |
| 覆盖任意玩家牌 | 高 |
| 让本次出牌立即获得 +1 | 中高 |
| 让不可观测区削弱玩家最高 Power 牌 | 中高 |
| 占据中心格 | 中高 |
| 单纯增加己方场上总 Power | 中 |
| 使用低 Power 牌进入普通空格 | 低 |
| 为了较小收益放弃一次合法覆盖 | 负分 |

首战 AI 不读取玩家手牌，也不搜索未来回合；只对当前合法动作结算后的局面评分。

## 10. 开发验收标准（文档确认后执行）

### 10.1 通用规则

- 3×3 共 9 格。
- 玩家固定先手。
- 双方轮流各出 1 张牌。
- 手牌永不超过 5 张。
- 合法打牌后手牌减少 1；场上增加或替换 1 个实例。
- Power 必须严格更高才能覆盖敌方牌。
- 相等或更低的非法覆盖不消耗手牌。
- 被覆盖和移除的牌不会再次抽到。
- 9 格均被卡牌占据后结算双方总 Power。

### 10.2 卡牌与效果

- 卡牌数据与引擎逻辑分离。
- 玩家牌库、怪物牌库、怪物策略分别配置。
- 所有效果先验证目标，再改变状态。
- 首战只实现第 7.4 节定义的四种效果模板。
- 首战 Power 修改均为永久修改，并保存基础 Power 与当前 Power。
- 没有效果目标时跳过效果，不阻止卡牌正常入场。

### 10.3 UI

- 不改变当前整体视觉方案。
- 卡面可读出名称、Power 和效果。
- 白色文字使用当前已配置字体。
- 只显示完成操作和理解状态所需的信息。

## 11. 需要本次验收确认的问题

请重点确认以下问题；它们会直接决定开发实现：

1. **起手与抽牌**：是否采用双方起手 5 张、首轮不抽，之后每次己方行动开始抽 1 张？
2. **满手处理**：手牌已有 5 张时，是跳过抽牌并保留牌库顶牌，还是烧掉牌库顶牌？
3. **平局**：满盘总 Power 相同，判平局、玩家胜还是怪物胜？
4. **无合法行动**：是否采用单方跳过、双方连续无法行动后按总 Power 结算？
5. **首战牌库**：是否接受第 7 节两套固定 12 张新手牌库及其数量？
6. **永久修改**：是否确认首战所有 `+1 / -1` 在该牌离场前永久有效？
7. **可选目标**：相邻目标不存在时，是否确认卡仍可入场、效果直接跳过？

第 5–7 项确认后，两套首战牌库即可直接转成研发配置；第 1–4 项仍属于通用对局规则，需要在开发前确定。
